# Finance web dashboard

Vite + React with real Clerk sign-in, configured by `GET /api/v1/config`. There is no demo identity or mock financial data. Build writes to the shared root `dist/`; **build web before userscripts**, since Vite clears that directory.

## Development origin

The browser client calls `${location.origin}/api/v1`, never the production host implicitly. Vite serves on `http://localhost:5173` and proxies `/api` to `http://localhost:8787`, preserving the original Origin header (`changeOrigin: false`). Run the local Worker on port 8787 in a separate process. The root integrator must set the local Worker's **development-only** `.dev.vars` override to `APP_ORIGIN=http://localhost:5173` and configure development Clerk credentials/authorized parties for that exact origin. Do not change the production origin or commit secrets. Vite does not proxy Clerk; its real SDK handles explicit sign-in.

## Independent Finance sessions

Bootstrap renews the own HttpOnly Finance cookie and validates `/me`/vault/key bindings independently of whether Clerk is loaded, signed in, or expired. Clerk signing out/expiring **does not** revoke the Finance session, forget remembered keys, hide history or trigger a new exchange. Existing access lasts according to the server's 90-day inactivity / one-year absolute session policy. Clerk is consulted only for an explicit new connection or sensitive step-up; expired absolute/idle credentials require explicitly signing in and connecting again.

An explicit application logout does revoke/forget and sign out Clerk. A different **signed-in** Clerk subject blocks old views immediately and clears the old Finance context before any new explicit exchange. The local identity binding records both verified Clerk subject and internal Finance account ID; legacy subject bindings are recognized. Failed explicit logout/switch cleanup leaves a blocked binding so a page reload cannot silently restore that old profile. Remembered CryptoKeys remain additionally bound to account ID + key version.

## Product validation, allocations and migration

Loaded/saved/restored product payloads use shared domain schemas for providers, provenance, dates, money, holdings and transactions. Settings must be own-property objects; allocation/card rule fields use the shared validators. Decrypted import validates **every** document, scope, nesting/key/size/date limit and duplicate before the first write. Bank history must be a single posting-day partition with `occurredAt` at that day's UTC midnight; portfolio occurrence time must equal provenance capture time. Malformed old capture-time bank histories are rejected, not silently re-aged.

Overview renders actual/target balances, fixed/excluded status, drift basis points and deltas from `calculateAllocations`. Edit `allocations.scopes` in product settings with explicit account/account type/currency/section and holding target definitions; there is no mixing of CPF/SRS/cash, currencies or liabilities. Unknown coverage and valuation denominators remain warnings. Ambiguous Maybank or partial-retention months never display exact remaining/eligible claims.

The settings page includes a 2 MiB legacy local config file chooser with explicit source product. It imports only configuration into separate encrypted review documents; it never authenticates to old servers or assumes matching email accounts. Legacy portfolio identifier targets require explicit mapping to current allocation scopes; bank templates require explicit bound-account mapping. Unsupported old encrypted files must first be decrypted/exported by the old tool.

Supported flows: explicit browser session exchange, cookie renewal, sign-out; vault creation with required recovery download acknowledgement, passphrase/recovery unlock, passphrase rewrap, opt-in indefinite IndexedDB key persistence, lock/forget; product/name/scope pairing inspection and code-bound approval; product-specific current settings editing with three-way reconciliation; paginated decrypted history; latest portfolio views and deduplicated retained bank history with corrections, provenance, incomplete/stale warnings and separate-currency aggregates; reference monthly caps from `@finance-tools/card-rules` with selected categories/merchant maps and UNVERIFIED rule warnings; session listing/revocation; encrypted and optional plaintext downloads of only granted namespaces; create-only fresh decrypted import; same-account authenticated encrypted restore. Imported settings are separate documents and must be explicitly reviewed/copied into the selected product's current editor.

Encrypted restore supports up to 64 MiB. It validates format, product, envelope versions, timestamps and duplicate IDs, unlocks the imported vault and authenticates every document before any mutation. A persisted encrypted-backup fingerprint permits resuming only the identical interrupted restore into the same account, preserving mutation UUIDs and skipping identical completed documents. Divergent existing data is never overwritten. Larger backups need streaming tooling; this UI does not silently claim to support them.

Deletion starts Clerk `multi_factor` reverification with a fresh email code. If Clerk reports `needs_second_factor`, the UI offers the enrolled TOTP authenticator, backup-code and phone-code factors returned by the installed SDK. Phone delivery is explicitly prepared for the selected enrolled phone ID before attempting its code. A fresh token is fetched only after `complete`, with DELETE confirmation and the same subject/session/account/lock epoch and uncancelled verification intent. Cancellation or an identity switch fences late completions. Unsupported factors and incomplete verification remain blocked with an explanation; they are not treated as success. Email verification must be enabled. The backend independently verifies fresh `fva` for both factors when enrolled, not merely JWT `iat`.

Browser session exchange is an explicit button action, never an effect/render loop. The browser remembers its Clerk-subject binding so switching identity cannot expose a previous account's cookie session or remembered vault key. Web Locks serialize cookie mutation/renewal across tabs. Refresh UUIDs persist before send and are reused on response loss. Transient network/contention/409/429/5xx errors preserve credentials and keys; a retry-renewal button avoids unnecessary new sessions. Definitive server 401 clears credentials and keys. Epoch guards invalidate late reads/writes/session acceptance, and prepared vaults bind both account and epoch. JWT subject/session metadata is checked against `/me` and cached account identity before allowing an old-account encrypted mutation to resume; JWT signature/authorization verification remains the server's responsibility. Principal changes invalidate the old controller without erasing another account's newly rotated shared credentials. Lock stays available during in-flight requests; notifications clear other same-origin tabs' decrypted views. Revoke-all deliberately renews the existing Finance session after locking views, so an expired access JWT does not require minting another Clerk-backed session.

## Integration verification

Root integrator owns dependency installation and build orchestration. The owned manifests include the card-rules workspace dependency; do not race another install. Run package typechecks, web build, userscript build and root tests. Client/API cross-integration is verified in Miniflare. The browser UI test runs actual React effects, Web Crypto, IndexedDB, same-origin credentialed fetch and page reloads in the preinstalled Chromium cache at `/ms-playwright`, using native CDP (no extra Playwright dependency/install required). It mocks Clerk and the API only in an esbuild test harness; neither fixture is imported by the production entry/config. It covers cookie restoration, remembered-key reload, Clerk expiration, explicit connection/logout, account switching, email-plus-TOTP/backup/phone deletion, and cancellation/switching during pending MFA. Set `FINANCE_TEST_CHROME` if the cache binary differs. Supported second-factor APIs were checked against installed Clerk 5.61.3 types; live Clerk delivery, authenticator and backup-code verification remain unverified. The deprecated package was not upgraded as part of this focused fix.
