# Finance userscripts

`node build.mjs` (or the package build script) bundles two self-contained esbuild IIFEs into root `dist/scripts/`:

- `portfolio.user.js`: Endowus, FSM and OCBC. Starts the allowlisted fetch/XHR capture bridge at document-start. A startup-only queue holds at most six events / four million JSON characters for at most 30 seconds, **in memory only**, to replay after remembered-key restoration or prompt unlock. Explicit lock/navigation clears it and disables further queuing. Otherwise unlock and reload the holdings route. Endowus joins require the same route/account context and request times within 15 seconds, allow union/subsets of goal IDs, flag missing/subset data and use the oldest actual component timestamp. Missing provider account context is explicitly unverified, not guessed from goal-set equality.
- `bank-subcaps.user.js`: UOB and Maybank. After unlocking, explicitly capture the supported visible, uniquely scoped card table. Normalization comes exclusively from `@finance-tools/provider-adapters`.

Install from `https://finance.laurenceputra.com/scripts/<name>.user.js` with a userscript manager supporting the declared legacy GM APIs. Each distributed script has separate pairing/session/storage. Create pairing, approve in the dashboard after inspecting name/scopes and supplying the code, return to redeem, then unlock the vault independently. Pairing never transfers keys.

The panel provides connect/redeem, passphrase or recovery unlock, lock/forget, disconnect, captured-history sync/pull, category assignment, settings JSON with three-way reconciliation, encrypted local-cache export/import and optional decrypted account export. Portfolio and bank scripts request separate product scopes; document writes carry their exact product. Product-specific current settings use `current_portfolio` and `current_bank-subcaps` IDs.

Bank captures flagged with unavailable account context stay ephemeral and cannot sync/import into persistent history. Enter a unique **masked** account label to bind that capture explicitly via the provider adapter; provider/card/masked label mappings are saved only inside encrypted settings. Bind each newly unidentified table deliberately, never assume the synthetic fallback is an account. Retained account-bound captures are aggregated with the domain package, deduplicating stable transaction IDs and displaying corrections and unknown coverage. Monthly calculations use `@finance-tools/card-rules`, selected categories and merchant maps. All reference rules are prominently **UNVERIFIED**, with source/version and unknown effective date; verify with the issuer. Optional user planning caps are not a substitute for those reference rules.

Portfolio target-versus-actual calculations use the shared `calculateAllocations` model: explicit account, account type, currency, asset/liability, optional goal and deposit scopes, holding target basis points or amounts, fixed/excluded positions, drift and deltas. Edit validated allocation settings in the panel, then review incomplete-coverage/unknown-value warnings. This is a balance comparison, never a recomputed time-weighted return.

Local capture tracking retains unsynced data across pulls and never silently truncates at 500. A 10,000-capture memory limit rejects an excess batch atomically with an explicit error; dirty captures are not evicted. Export/sync before navigation or locking (privacy lock intentionally clears decrypted memory). Manual sync persists bank captures as **daily posting-date partitions**, not capture-time documents, so recapturing old transactions cannot extend their retention. Capture observation time remains separate provenance. Local exports use the same daily partition format. Maybank snapshot-local identities use latest-window lower-bound/unknown-coverage semantics, and exact eligible/remaining amounts are suppressed for ambiguous or partial-retention months.

Background sync is opt-in, default off, consent-bound to the internal Finance account in GM. It debounces capture/unlock, excludes unidentified cards, singleflights uploads and retains failed dirty captures for explicit retry. It does not create login sessions or retry permanent failures in an unbounded loop.

Legacy local config JSON import is bounded to 2 MiB and explicitly selected as portfolio or bank-subcaps. It never contacts old remote services or matches email identities. Imports create encrypted review documents, not current-setting overwrites. Portfolio legacy code/goal targets require manual current account/holding/currency scope mapping; bank templates can be assigned only with explicit current account IDs. Old encrypted transport formats must first be exported/decrypted using the old tool; automatic unattended transport migration is not implemented.

Opt-in indefinite remember in GM requires recovery-key unlock: GM cannot persist nonextractable `CryptoKey` objects, so the recovery key is explicitly stored as privileged key material, never a plaintext passphrase. This grants access to anyone controlling your manager profile. Lock/disconnect deletes remembered material and clears other tabs via GM change notifications. Browser dashboard instead stores a nonextractable vault key in IndexedDB.

Refresh has per-tab promise singleflight and cross-host owned bakery-ticket leases with shared ownership fencing, heartbeat renewal and post-response ownership checks. An attempt UUID is persisted before sending `X-Finance-Refresh-Id` and reused after lost responses. Network errors, contention, 409, 429 and 5xx retain keys/credentials; definitive server 401 clears them. GM requests are anonymous, cookie-free and hardcoded to Finance. Opaque rotated refresh credentials remain in GM; own access JWTs stay in memory. Epoch guards and serialized writes prevent late acceptance after lock/disconnect/account switches. Bridge wrappers expose only allowlisted financial response payload events, never headers, cookies, GM APIs, JWTs or vault keys. Firefox uses `exportFunction` when available; installation is guarded and partial native-wrapper installations are rolled back. Fetch responses/statuses and XHR methods/statuses are preserved. Page-origin data is untrusted; it is not authentication or command input. No remote runtime code is fetched.

Local encrypted snapshot caches and queued history writes older than the rolling UTC three-calendar-month cutoff are physically deleted. Settings are not purged. Only encrypted envelopes and metadata fingerprints are persisted for retryable writes. Separate encrypted mutation receipts preserve retry UUIDs even when concurrent edits target one document; no low-entropy financial plaintext digest is persisted. Same mutation payload reuses its UUID and ciphertext; conflicts pull/decrypt and reconcile independent settings edits or append-only transaction/holding records by stable ID. Divergent same-record edits require review; merged captures carry an explicit incomplete merge flag. Sync never force-overwrites. Cache import supports up to 64 MiB, authenticates/preflights all documents before storing, and rejects cross-account/product or ephemeral captures; larger files need streaming tooling. Explicit local plaintext export can save unsynced **bound** captures, but excludes unidentified bank captures and includes only granted namespaces.

## Verification / limitations

The current scripts are **not service-independent local-first tools**: capture/calculation UI requires an existing Finance connection and unlocked vault. They can calculate locally and export unsynced bound captures after that unlock, but a completely unpaired user cannot use a standalone local mode. Remembering in GM requires recovery-key unlock rather than passphrase-only unlock; this is deliberate because GM cannot persist nonextractable CryptoKeys safely. Manual sync remains the default; background sync requires explicit account-scoped consent.

Build output includes version 0.1.0, exact matches, document-start, explicit GM grants, Finance-only `@connect`, and public update/download URLs. Build web first, then scripts. Client tests cover transport, refresh concurrency, account binding, revoked-session cleanup, locking, retention, reconciliation and encrypted retry persistence. Live portal and userscript-manager bridge compatibility (notably Firefox cross-realm wrappers), live pairing, Clerk and backend integration still need end-to-end verification. The bridge is endpoint-allowlisted and will require a deliberate update if providers change host/path/methods.
