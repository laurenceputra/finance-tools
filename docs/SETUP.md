# Production setup checklist

## Verified state and remaining blockers

- D1 `finance-tools` and the deployed Worker already exist; do not create duplicates. Tracked `wrangler.jsonc` contains only placeholders. Keep the existing UUID and production hostname in private Builds variables, not Git.
- Payload storage is D1-only; R2 enablement and Workers Paid are not requirements.
- Production Clerk configuration/secrets and end-to-end application readiness are **not certified** by an existing deployment. Production Workers Free CPU/quota compatibility has not been measured.
- Verify Builds connection, main-only branch settings, selected token permissions and routing in the dashboard. This change performs no deployment, migration, provisioning or remote configuration writes.

## Cloudflare dashboard

1. Select the intended Cloudflare account. The configuration targets Workers Free and has no Paid-only subrequest override. Do not change billing without operator approval.
2. Locate the existing `finance-tools` database in **D1** and copy its UUID privately into Builds variable `CLOUDFLARE_D1_DATABASE_ID`; do not create another database or enable R2. Its initial migration defines the D1-only schema, including required immutable encrypted payloads.
3. Open the existing `finance-tools` Worker in **Workers & Pages** and its **Settings → Builds**. Verify the connected repository; authorize a Git connection interactively if one is not yet configured. Do not create a duplicate Worker.
4. Set production branch **main** and root directory **/** (repository root). Build command: `corepack pnpm install --frozen-lockfile && corepack pnpm check`. Deploy command: `corepack pnpm deploy:cloudflare`.
5. Under the Worker's **Settings → Builds**, disable nonproduction branch builds/preview builds. Keep production deployments automatic on main only. Never add Pages or GitHub deployment workflows. Wrangler also disables workers.dev and preview URLs.
6. Add private **Builds variables** `CLOUDFLARE_D1_DATABASE_ID` and `APP_HOSTNAME`. The latter is a bare DNS hostname (example only: `finance.example.com`), without protocol, port, path, wildcard or trailing dot. It is required during both build and deployment: userscript metadata and API/pairing links are compiled from it. Browser API requests and install links use the current application origin. Local/validation builds without `APP_HOSTNAME` use the example domain; do not install those artifacts as production scripts. Preflight requires Cloudflare-provided `WORKERS_CI=1`, `WORKERS_CI_BRANCH=main` before any remote migrations; do not spoof these locally. These flags are a safety check, not a security boundary. It validates the template, variables and disabled previews, then atomically writes ignored root `wrangler.deploy.jsonc` with mode 0600. The config injects the DB UUID, custom-domain route and HTTPS `APP_ORIGIN`; keeping it at root preserves Worker/assets/migration relative paths. Both migration and deployment use this same generated config. Stale output is removed before validation and the wrapper cleans up on success/failure. Only `dist` is uploaded as assets, never the private config. Use native **Settings → Builds → API token** authentication: [Workers Builds manages it automatically](https://developers.cloudflare.com/workers/ci-cd/builds/configuration/). Do not define custom `CLOUDFLARE_API_TOKEN` or `CLOUDFLARE_ACCOUNT_ID`. Default token permissions do **not** include D1; the selected token must include **Account → D1 → Edit** for remote migrations alongside Worker/assets/custom-domain deployment permissions. Adjust the selected token under **My Profile → API Tokens**, or select an appropriately scoped token in Builds. Account selection comes from native Builds context; no tracked account ID is required.
7. Add Worker runtime secrets listed below through **Settings → Variables and Secrets** in the dashboard only. Keep actual secrets out of Git, GitHub validation, build variables, logs and client bundles. If dashboard workflow deploys immediately when connecting, supply secrets/resources first or keep the build blocked until setup is complete.
8. After a successful main build, confirm all migrations applied before deployment, the D1 binding exists, the custom domain `finance.example.com` is routed to this Worker, previews/workers.dev remain disabled, and hourly Cron `0 * * * *` is registered. Verify login, pairing, restore, vault unlock, scoped sync, paged encrypted export and deletion with an authorized test account. Monitor Free CPU (10 ms), D1 daily read/write quotas, cleanup backlog and shared database capacity (500 MB including retained versions/indexes/metadata). Per-account 64 MiB logical quotas do not reserve database capacity. Passing local tests alone is not verification of these production flows or runtime limits.

### Consolidated initial schema and local development

The initial schema was consolidated into `0001_initial.sql` before first deployment; future production changes require new backward-compatible migrations, not edits to the applied initial migration. An existing disposable local development database initialized with an earlier schema needs recreation before applying the initial migration. No actual local or remote reset has been performed. Preserve any local user data: recreation is only appropriate for disposable data, and any destructive action requires separate authorization and a preservation plan when needed.

## Clerk dashboard

1. Create/select a **production** Clerk instance; finish its production-domain/DNS setup for this application and configure allowed origin/authorized party `https://finance.example.com`.
2. In **Sessions → Customize session token → Claims**, add `"aud": "finance-tools"` to the existing claims object and save. Use the default session token requested by `getToken()`; **do not substitute a JWT template**, remove default claims, or override `iss`, `sub`, `sid`, `azp`, `iat`, `exp` or `fva`. The server requires the default session identity and factor-verification claims. Confirm the SDK/version supports signed `fva` and reverification; fail closed if unavailable.
3. Copy the instance's actual issuer URL to `CLERK_ISSUER` (not the app origin); set `CLERK_AUDIENCE=finance-tools`. Retrieve production publishable/secret keys from **API Keys**. Optional `CLERK_JWT_KEY` is the configured public verification key, not a signing secret.
4. Under **Webhooks → Add endpoint**, use `https://finance.example.com/api/v1/webhooks/clerk`, subscribe to both `user.deleted` and `user.updated`, and store the endpoint signing secret as `CLERK_WEBHOOK_SECRET`. Deletion cleanup relies on deleted events; ban/unban state relies on updated events. Verify signed deliveries after deployment.
5. Runtime secrets: `CLERK_PUBLISHABLE_KEY`, `CLERK_SECRET_KEY`, `CLERK_ISSUER`, `CLERK_AUDIENCE`, `CLERK_WEBHOOK_SECRET`, independent random 32-byte base64url `ACCESS_JWT_SECRET`, `SESSION_WRAP_SECRET` and **`VAULT_WRAP_SECRET`**; optional `CLERK_JWT_KEY`. Never reuse the session wrapping secret for vault recovery. Missing/malformed vault secret produces `vault_wrap_not_configured`; new Standard exchanges fail closed. Preserve this secret with authorized operator recovery procedures: replacement/rotation needs a separate server-wrap migration. Never expose Clerk secret/webhook/server signing keys through `VITE_*`. If the web app requires a build-time publishable key, supply only its documented public variable.

Clerk session tokens establish identity; application refresh sessions are independent. Fresh sign-in automatically exchanges once and opens Standard encryption; legacy/non-null vaults stay Private. Browser restore works from a valid application cookie without a current Clerk login. Enable email reverification and enrolled MFA for both deletion and mode changes: server-verified factor ages are required, not merely a recently issued token. No live Clerk/production configuration is verified by the local fixtures.

Apply additive migration `0002_vault_modes.sql` through the existing authorized main Builds workflow, never by rewriting `0001_initial.sql`. It adds separate server-wrap metadata, deletion cleanup, and caps existing sessions to 30 idle/90 absolute days based on original millisecond dates (already-expired sessions are not renewed). Supply `VAULT_WRAP_SECRET` before enabling the new default. This implementation does not provision that production secret or deploy migrations.

## Local and GitHub validation

Use Node 22, `corepack pnpm install --frozen-lockfile`, then `corepack pnpm format:check` and `corepack pnpm check`. GitHub has no deployment credentials and performs validation only. The current real-browser UI test uses a preinstalled Chromium executable from `/ms-playwright` (or `FINANCE_TEST_CHROME`) and explicitly skips when absent, including on ordinary GitHub runners. No browser download is performed by CI; a passing CI run may therefore omit browser UI coverage. If browser tests become mandatory CI checks, first declare the intended browser tooling/version and add an explicit browser-install/setup step rather than invoking an undeclared latest Playwright package.
