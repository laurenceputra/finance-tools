# Security boundaries

## Standard and Private encryption

New accounts default to **Standard**, with a random 256-bit data key recoverable by the service after verified sign-in. A dedicated independent 32-byte base64url `VAULT_WRAP_SECRET` wraps it using AES-256-GCM, fresh 96-bit IVs and purpose/version/account/key-version-bound AAD. The wrap lives separately from public vault metadata in D1. It never appears in `/vault`, exports, mode receipts or client storage. Standard is **not end-to-end private from the operator**: the Worker can recover the key. Missing/malformed configuration fails closed. Losing/replacing the wrapping secret without migrating wraps loses recoverability; wrap-key rotation is not implemented.

Existing non-null version-1 vaults remain **Private**; no migration uploads their keys. Private version-2 supports account/version-bound key files (`finance-tools-key`, version 2), and legacy `{version:1,accountId,recoverySecret}` files intentionally remain supported for unlock. A passphrase wraps the same random data key using PBKDF2-SHA256 (600,000 iterations, random 16-byte salt) and AES-GCM. An independent 256-bit recovery/key-file secret wraps the same key. Losing both passphrase and key/recovery file loses access: neither Clerk nor the service can recover a Private key.

Mode changes require an authenticated browser app session, a fresh matching server-verified Clerk subject, first-factor verification and enrolled MFA. Atomic revision CAS and payload-bound permanent receipts make exact retries safe after response loss; mode receipts contain only revision/mode/key-version metadata, never raw keys or server wraps. Standard→Private locally wraps the existing key, tests its new recovery wrapper, and requires key-file download/confirmation before commit clears the server wrap. Private→Standard requires local unlock and explicit trust consent; conversion decrypts an existing wrapper transiently instead of making ordinary CryptoKeys extractable. Same key/version is retained in both directions; client-side wrapper authentication/continuity checks protect the supported UI flow, **not against an authenticated malicious owner deliberately submitting a different key/wrapper for their own account**. There is no cross-account key substitution. No data-key rotation is implemented.

Switching to Private deletes the active server wrap but cannot retroactively erase operator/database backups, old Private wrapper receipts, downloaded files, already released keys or other devices' cached keys. Mode/revision changes clear this client's remembered key and decrypted views when observed; already acquired keys cannot be remotely erased. Lock clears local key material and fences in-flight responses; Standard unlock then requires a deliberate action rather than a background reinitialization.

## Local data and sessions

All document envelopes use fresh 96-bit IVs and 128-bit tags. Document AAD is UTF-8 JSON array `["finance-tools",accountId,namespace,documentId,schemaVersion,keyVersion]`; Private wrapping namespace is `vault`, IDs `passphrase` and `recovery`. Validate strict schemas, canonical base64url, envelope sizes and KDF bounds before derivation. Generic JSON decryption is not application schema validation: validate decrypted financial data separately.

Ordinary CryptoKeys are nonextractable. Standard raw keys are transient, never automatically persisted. Private indefinite local unlock is opt-in: a nonextractable key in IndexedDB or an explicit recovery secret in GM storage. Clear on lock/logout. This is not OS/hardware protection, browser-profile-theft protection or defense against compromised same-origin JavaScript/extensions; GM storage offers no encryption guarantee. Never automatically persist passphrases, raw keys or recovery files. Sensitive mode requests bypass the generic durable mutation queue.

App access JWTs last 15 minutes; rotating refresh sessions last at most 30 idle/90 absolute days. Migration caps existing timestamps without granting a fresh lifetime. Cookie lifetime is capped to the remaining absolute deadline. Restoring/refreshing app access needs no live Clerk session. Explicit logout revokes app access and clears keys, signs out Clerk, and suppresses automatic reconnection. Revoke-all atomically advances the account epoch to fence concurrent session issuance. Signed ban/unban state and deletion are enforced in persisted authorization checks.

Server sees metadata (account, namespaces, IDs, revision, sizes, occurredAt); encryption does not conceal it. XSS or a malicious release can capture unlocked data. Never log tokens, pairing secrets, plaintext, keys, envelopes or webhook bodies. Paired userscripts may release the Standard account key after persisted scoped-session checks; **possession of a shared account data key is not cryptographic product isolation**, although the API independently enforces product/namespace grants. Pairing itself carries no key; Private requires separate local unlock.

## Storage, backups and deletion

D1 stores encrypted document envelopes once per immutable version. Existing command triggers atomically enforce active account/session, scopes, key version, quotas, CAS and receipts. Failed mutations leave no partial payload or pointer. Cleanup rechecks document and receipt references in bounded batches; expired history receipts retain identity/hash. Mode changes use a separate atomic conditional update/receipt transaction with persisted eligibility and quota checks, not the document mutation payload channel.

Each signed-cursor export page reauthorizes its browser session; exports are not atomic snapshots. Server exports never include server wraps/raw keys. A **portable Standard backup requires a separate explicit export passphrase**: the client transiently releases the key and writes a Private-style passphrase/recovery wrapper into the encrypted backup (no raw key). Keep that passphrase separately; merely downloading server metadata does not create a recoverable backup. Private backups keep their existing wrappers. Restore authenticates all retained ciphertext/application data before writes; an empty auto-initialized Standard destination reencrypts with its existing key rather than replacing it, and exact interrupted restores can resume. Decrypted exports contain sensitive plaintext.

Deletion synchronously clears the active server wrap and leaves a durable account tombstone before bounded cleanup. Fresh signed Clerk factor ages plus trusted MFA enrollment are required for deletion and mode changes; refreshing a JWT alone is not reverification. Production Clerk delivery, live provider support and Workers Free CPU/quota suitability require separate authorized live verification; local fixtures are not certification.
