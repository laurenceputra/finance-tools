# Security boundaries

Clerk login proves identity; it does not decrypt the vault. A separate passphrase wraps a random 256-bit vault key using PBKDF2-SHA256 (600,000 iterations, random 16-byte salt) and AES-256-GCM. An independently random 256-bit recovery secret wraps the same key. Save recovery secret offline: neither operator nor Clerk can recover lost credentials. All envelopes use fresh 96-bit IVs and 128-bit tags. AAD is UTF-8 JSON array `["finance-tools",accountId,namespace,documentId,schemaVersion,keyVersion]`; wrapping namespace is `vault`, IDs `passphrase` and `recovery`. Passphrase change rewraps same key, preserving documents; key rotation is a separate migration not implemented here.

Validate schemas, canonical base64url, envelope sizes and KDF bounds (600,000–2,000,000) before derivation. Generic JSON decryption is not application schema validation: callers must validate decrypted data. CryptoKey is nonextractable; persistence may store that key in IndexedDB or an explicit recoverable local representation. Indefinite local unlock is **opt-in**, off by default; clear on explicit forget/reset. It cannot promise OS/hardware protection, browser-profile theft protection, or defense against compromised same-origin JavaScript/extensions. GM storage offers no encryption guarantee. Never automatically persist passphrase or recovery secret.

Server sees metadata (account, namespaces, IDs, revision, sizes, occurredAt); encryption does not conceal it. XSS or a malicious release can capture unlocked data. Use CSP, dependency review and scoped script permissions. Never log tokens, pairing secrets, plaintext, recovery material, envelopes or webhook bodies. Use rate limiting, atomic refresh/CAS operations and account ownership checks. R2 cleanup and SQL tombstones need deletion tests. Export contains ciphertext, not a decrypted backup. No recovery escrow.

Persisted product scopes (`portfolio`, `bank-subcaps`) are independent from namespace scopes; display labels and document prefixes never grant access. Refresh retry successors are encrypted under a separate server wrapping secret for at most 120 seconds; clients persist the logical UUID during retries and serialize refreshes. Account deletion uses server-verified Clerk factor ages plus trusted MFA enrollment state, not just JWT issuance freshness. Revealing recovery secrets or exporting decrypted data requires explicit local unlock/confirmation; the server export endpoint only exposes ciphertext. Do not claim a step-up UI proves server enforcement unless the corresponding signed claims are checked.
